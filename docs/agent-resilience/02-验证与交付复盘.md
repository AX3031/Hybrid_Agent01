## 1. 验证体系长什么样

项目原来没有任何自动化测试。这次补的最小可用验证体系是：

```
tests/                          ← 用例（标准库 unittest，不加依赖）
├── fakes.py                    ← 假模型：不联网、不花钱，按脚本调工具
├── test_agent_resilience.py    ← 异常转消息 / 重试分类 / 悬空调用修复
├── test_tool_verification.py   ← 五类文件操作的后置校验
└── test_agent_tools.py         ← 联网搜索的失败语义 / 重试分类表

scripts/verify_agent_resilience.py
└── 跑全部用例 + 记录环境/commit/逐条耗时 → docs/agent-resilience/evidence/verify-*.json
```

为什么不用 pytest：`pyproject.toml` 里没有测试依赖，为了"能验证"给运行环境加一个包不划算。
`unittest` 是标准库，`python -m unittest discover` 就能跑，任何机器都能复现。

### 1.1 假模型是什么

`tests/fakes.py` 的 `ScriptedToolModel` 是一个 `BaseChatModel` 子类：

- 前 N 轮返回指定的 `tool_calls`；
- 之后返回固定文本；
- 不访问网络，不需要 API Key。

这样"工具失败 → 错误消息 → 模型继续"这条链路可以**确定性地**测，
不受模型随机性、额度、网络影响。

## 3. 真实链路冒烟（不是假模型）

用例证明的是"机制对"，冒烟证明的是"接上真模型、真工具、真中间件也能跑"。

### 3.1 只读工具成功路径

```text
输入：只调用 computer_use 的 screen_size 动作，用一句话告诉我当前屏幕分辨率
TOOLS: [('computer_use', ...)]
ANSWER: 当前屏幕分辨率为 1920 x 1080 像素。
```

### 3.2 联网搜索成功路径

```text
输入：调用 web_search_baidu 搜索「哈基米是什么梗」
日志：工具 web_search_baidu 调用成功 → 再次调用模型（3 条消息）
结果：模型基于搜索结果给出总结
```

> 说明：改造前日志里这条链路出现过 401 且被吞成空字符串；本次运行时密钥可用，
> 因此记录的是成功路径。"401 不被吞"由离线用例 `test_http_error_is_not_swallowed` 覆盖。

### 3.3 工具崩溃路径（最关键）

把 `computer_use` 临时替换成"必崩"实现，跑真实 Agent：

```text
TOOLS: [('computer_use', 'error')]
日志：工具computer_use调用失败 → [tool error]异常已转为错误消息 → 再次调用模型
ANSWER: 本轮操作被中断：`computer_use` 的 `screen_size` 动作执行失败，
        原因是“模拟工具崩溃（冒烟用）”……
```

结论：**没有抛异常、没有整轮失败、模型拿到了真实原因并如实回答。**

顺带发现一个真问题：模型在回答里写"已重试一次"，实际并没有重试。
于是把错误消息改成了"系统不会自动重试所有工具，所以不要在回答里声称已重试"。
这类"模型虚报"只能在真实链路里发现，单元测试发现不了——这也是为什么要保留冒烟。

## 5. 复盘四问

### 5.1 做了什么

把"工具失败后 Agent 就停"的四个根因分别修掉：错误可见、有限重试、结果校验、会话自愈，
并建立可重复运行的验证体系。

### 5.2 证据是什么

- `evidence/verify-*.json`：20/20 通过；
- 三次真实链路冒烟（成功、搜索、崩溃）；
- `git log`：本阶段提交（见第 8 节）。

### 5.3 哪里还不完善

按方法论区分三类，不混成一句"继续优化"：

**已知缺口（明确没做，知道为什么）**

- `run_command` 没有做"退出码非 0 → error"的判定。`git diff --exit-code` 这类命令非 0 是正常语义，
  需要先定义白名单，不能一刀切。
- `computer_use` 的截图没有核对"文件确实生成"。结果里带路径，可以做，但这次没扩。
- 没有 CI。验证脚本是手动的。

**未知风险（怀疑但没验证）**

- `ToolRetryMiddleware` 的重试发生在 `HITL` 确认之后；如果用户确认后重试，确认卡片只弹一次。
  这对只读工具无影响（本就不需要确认），但以后若把写操作加入重试名单，需要重新设计确认语义。
- 长会话里自愈会不断追加 `[未执行]` 占位消息，理论上会让上下文变长；目前没有清理策略。

**有意不做（非目标）**

- 多 Agent 评审、自动"验收节点"：延迟和成本都高，且当前任务的失败模式用中间件就能覆盖。
- 换测试框架、加 mock 库：标准库够用。

### 5.4 下一步

1. 把验证脚本接进 pre-push 或 CI；
2. 定义 `run_command` 的退出码语义（哪些非 0 算失败）；
3. 评估"校验失败后自动重试一次"是否安全（当前只报告，不自动重试）。

## 6. 回滚方式

本次改动没有数据迁移，回滚就是代码回滚：

```powershell
git revert <本次提交的 commit>
```

单独关掉某个能力也可以（不用回滚全部）：

| 想关掉 | 怎么做 | 影响 |
| --- | --- | --- |
| 自动重试 | 从 `react_agent.py` 的 `middleware` 列表移除 `tool_retry_middleware` | 只读工具不再自动重试 |
| 异常转消息 | 移除 `tool_error_middleware` | 工具异常会重新打断整轮（回到旧行为） |
| 结果校验 | `monitor_tool` 里去掉 `enrich_tool_message` 调用 | 审计状态只反映工具自述 |
| 会话自愈 | `execute_stream` 里去掉 `_repair_pending_tool_calls` | 老会话崩溃后仍会留脏历史 |
