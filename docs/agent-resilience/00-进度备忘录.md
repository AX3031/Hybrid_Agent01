## 3. 关键决策（为什么这么选）

| 决策 | 选择 | 理由 / 被否掉的方案 |
| --- | --- | --- |
| 工具异常怎么办 | `ToolErrorMiddleware` 在最外层转成 `ToolMessage(status="error")` | 否掉“改 `monitor_tool` 自己造 ToolMessage”：会把日志/审计/异常捕获揉在一起，且 `ToolInvocationError` 由 ToolNode 自己处理，职责混乱 |
| 重试范围 | 只对幂等/只读工具重试，且只重试瞬时错误（超时/连接/429/5xx） | 否掉“全局重试”：`write_text_file` 追加写、`delete_path`、键鼠点击都不幂等，重试会放大副作用；401/403 重试只会更慢更贵 |
| 重试失败后 | `on_failure="error"` + 外层错误中间件兜底 | 否掉“返回一段文本继续”：异常会被当成正常结果，模型无法区分成功与失败 |
| 结果验证放哪 | `monitor_tool` 内部、写审计之前调用 `verify_tool_outcome()` | 否掉“再加一个中间件”：会多一次包裹、审计状态和校验状态可能不一致 |
| 悬空 tool_call | 提交新消息前用 `update_state(as_node="tools")` 补 error ToolMessage | 否掉“直接清空会话”：会丢掉用户上下文；也否掉“靠提示词让模型忽略”：API 层就可能 400 |
| 测试框架 | 标准库 `unittest` | 项目无 pytest，`pyproject.toml` 无测试依赖；不为了测试给运行环境加包 |

## 4. 已知限制 / 后续待办

- `verify_tool_outcome` 只覆盖文件系统五类操作（写/建目录/移动/复制/删除）；`run_command` 的退出码、`computer_use` 的画面结果仍需模型自己判断。
- 重试只覆盖 `web_search_baidu` 这类会抛网络异常的工具；`os_tools` 内部把错误转成字符串返回，不触发重试（这是有意保留的行为：它们的失败是确定性的）。
- 悬空调用修复依赖 `create_agent` 的节点名 `tools`；升级 LangChain 后需要回归第 1 阶段的用例。
- 未接入 CI：验证脚本是手动的，后续可挂到 pre-push 或 GitHub Actions。
- `fetch_external_data` 注解 `str` 实际返回 `dict` 的问题仍未处理（历史技术债，与本阶段无关）。
