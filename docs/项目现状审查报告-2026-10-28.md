## 0. 先看结论

**一句话：这是一套“守卫层明显领先、能力层明显滞后”的单机 L2 原型。它已经能防住很多误操作，但还没有证明自己能稳定完成真实任务。**

### 0.1 六个判断

1. **工程与安全设计高于同类原型。** 任务卡、只读、预算、急停、批次回滚、PIN、审计、离线用例都是真代码，不是提示词。这一点很难得，应该保留。
2. **但“能不能把活干成”没有基线。** 193 条用例全部使用假模型；没有真实任务成功率、成本、时延、人工介入次数的统计。项目自己的方法论说“先造尺子”，这把尺子还没有用在 Agent 本身上。
3. **长任务仍是主要失败面。** 一次真实桌面任务：18 次工具调用、20 次审批、约 5.9 元、最终验证失败。失败链是“OCR 找不到 → 猜坐标 → 焦点不明 → 重复点击 → 用户拒绝 → 预算熔断”。
4. **缺三块关键能力：协议层、状态 grounding、独立验证器。** 这不是“再加几个工具”能补的，而是架构层的缺口。
5. **安全上仍是 L2。** `.env` 可读、审计含原文、无网络出口白名单、无系统级沙箱；PIN 是“同机第二主体”，挡不住同一 Windows 用户下的恶意程序。
6. **产品化几乎没开始。** 真实业务数据是模拟的、没有安装包/鉴权/多用户/模板，术语对非技术用户不友好。

### 0.2 成熟度评分

以下评分是作者基于当前代码和一次真实运行的主观判断，用于横向比较，不是标准认证：

| 维度 | 分数 | 理由 |
| --- | --- | --- |
| 能力覆盖 | 5/10 | 文件、系统、桌面都有，但长任务和业务深度不足 |
| 任务可靠性 | 4/10 | 真实任务 18 步失败/超预算；GUI 结果无法自动验证 |
| 安全（防误操作） | 7/10 | 守卫层完整，回滚/预算/PIN 都是真机制 |
| 安全（防攻击/泄露） | 3/10 | L2、`.env` 可读、审计原文、无出口控制 |
| 工程可维护 | 6/10 | 测试/文档好，但单体、无 CI、文档漂移 |
| 产品可用 | 3/10 | 无安装、无鉴权、无模板、无真实业务数据 |
| 文档 | 8/10 | 丰富、诚实，但已经出现明显漂移 |
| **综合** | **5/10** | **受控原型可用，生产级产品还早** |

### 0.3 如果只做三件事

1. **造尺子**：20–30 个真实任务 × 3 次运行，先测出成功率、成本、时延、人工介入次数。
2. **改审批**：把“每步确认”改成“范围授权”，只拦不可逆/对外副作用；否则用户一定机械批准。
3. **加协议**：先接 2–3 个 MCP/CLI/浏览器 DOM 适配器，把 GUI 留给没有接口的应用。

## 2. 项目做对了什么（应该保留）

在批评之前，先说清楚这个项目真正的资产。很多同类原型只有“提示词 + 几个工具”，这个项目已经有了一套可执行的治理骨架。

### 2.1 把“提示词约束”变成了“代码判据”

`agent/guard/` 这一层是项目最有价值的部分：

- **任务卡**：目标、范围、允许/禁止动作、预算、有效期；
- **只读模式**：在工具层和中间件层双重拒绝；
- **R0–R3 分级**：只读 / 可撤销 / 难逆 / 不可逆；
- **批次回滚**：写、覆盖、追加、建目录、移动、复制、删除都进批次；
- **预算与急停**：模型调用前短路，`STOP` 文件独立于模型；
- **单任务锁**：同一时刻只允许一个任务操作本机；
- **PIN + HMAC**：R2/R3 需要第二主体，执行侧验签并绑定任务/批次/动作；
- **机器判据**：任务结束由代码核对存在性/文件数/哈希/文本包含。

这套东西的方向完全正确：**不要用提示词代替确定性判据**。这是项目最值得保留的“护城河”。

### 2.2 失败韧性不是“模型自己扛”

- `ToolErrorMiddleware` 把工具异常转成 `status=error` 的 ToolMessage，ReAct 循环不崩；
- `ToolRetryMiddleware` 只对幂等/只读工具重试 2 次，且只重试超时/断连/429/5xx；
- `repair_thread_state()` 在下次提问前补齐悬空 `tool_call`，避免脏历史把模型带偏；
- `verification.py` 在写审计前做文件级后置校验，校验不过就把状态改成 `error`。

这些细节说明作者理解“Agent 的失败是常态”，而不是假设工具永远成功。

### 2.3 可追溯性明显高于同类原型

- `logs/audit_YYYYMMDD.jsonl` 记录 `task_id/batch_id/step_no/reversibility/approver/approval_token`；
- 侧边栏可以按批次回放；
- 确认卡片用大白话说明“做什么、目标、风险、影响范围”；
- 安全报告诚实地区分了“真控制”和“看起来像控制”。

### 2.4 工程习惯好

- 193 条离线用例，不联网、不花钱；
- 验证脚本输出证据 JSON；
- CHANGELOG 按 Keep a Changelog 维护；
- AGENTS.md 给 AI 编码助手定了阅读顺序；
- 文档密度高，且愿意写“已知限制”。

### 2.5 产品化方向是对的

- 快速任务卡降低了使用门槛；
- 技能库尝试把一次成功经验沉淀为下一次的提示；
- 确认卡片说人话；
- 对“发送/付款/登录”有明确的交回给人的意识。

**总结**：这不是一个“玩具 demo”，而是一个有治理意识的原型。问题不是“做得差”，而是**安全壳跑在了能力内核前面**。

## 3. 发展不足

下面按“能力与效果 / 产品与业务 / 工程与维护”分组。每一条都给出证据、影响和建议优先级。

### 3.1 能力与效果

#### N1. 没有真实评测尺，所有“变好了”都是感觉

**证据**：

- 193 条用例全部使用 `ScriptedToolModel` 假模型，不联网；
- 没有 Golden Set、没有真实任务集、没有 baseline 快照；
- 没有统计任务成功率、首次成功率、人工介入次数、单次成功成本、P50/P95 时延；
- `docs/06-长期改造经验与方法论.md` 自己写“先造尺子”，但这把尺子只用在 RAG 改造上，没有用在 Agent 上。

**影响**：

- 无法判断某次改动是“真的提升”还是“换了一种失败方式”；
- 无法向客户/自己证明 ROI；
- 无法做阶段门（gate），只能凭感觉继续加功能。

**优先级：P0（最高）**。没有这一项，后面的优化都是闭眼调参。

---

#### N2. 长任务仍然靠运气：一次真实任务的失败链

这是本次审查最有说服力的证据。2026-10-28 10:32:25–10:35:02，一次真实模型运行（非离线用例），目标是打开即时通讯软件、找到联系人并发送一条消息。审计批次 `B20261028-103225-1597` 的结果：

| 指标 | 数值 |
| --- | --- |
| 工具调用 | 18 次，全部是 `computer_use` |
| 审批次数 | **20 次** |
| 模型调用 | 20–21 次 |
| 费用 | **5.87 元**（触发 5 元费用上限） |
| 时长 | 约 2 分 37 秒 |
| 工具错误 | 1 次 |
| 最终状态 | `budget_stop` + `task_verification=failed` |

失败链可以拆成五层：

| 层 | 发生了什么 | 说明 |
| --- | --- | --- |
| Grounding | `click_text("搜索")` 两次都没找到文字，改用坐标点击 | OCR 对小字号/自绘界面不可靠 |
| State | 连续 `type_text` 联系人、消息，但没有确认焦点窗口 | 无法证明文字落到了正确的输入框 |
| Recovery | 同位置第 4 次重复点击只收到“换策略”提醒；模型没有换策略 | 软提醒不能改变模型行为 |
| Parameter | `click(x=[150, 85], y=85)` 把 x 传成数组，工具报错 | 模型参数类型错误仍会发生 |
| Approval | 18 次工具调用产生 20 次审批；用户最后两次拒绝 | 审批疲劳的教科书案例 |
| Verification | 没有配置机器判据；最终 `failed` | 无法证明“消息发出去了” |

**关键结论**：这不是某一个 bug，而是“状态 grounding 缺失”的必然结果。模型不知道“当前焦点在哪、上一步到底改变了什么”，只能靠截图和坐标猜；守卫层能拦住越界，但拦不住“在允许范围内做错”。

---

#### N3. 缺状态 grounding：截图是“有损渲染”，项目却把它当唯一事实

`疑问与回答.md` 里有一个很准确的判断：**截图只是底层程序状态的一种有损渲染；不同程序状态可以产生完全相同的像素。** 当前项目基本停留在“截图 + OCR + UIA 树”的感知层，但没有把感知变成“状态”：

- 每步没有记录“前台窗口/pid/焦点控件/UIA 树哈希/文件统计”；
- 没有“连续 N 步状态无变化 → 判定无进展”的机制；
- 没有子目标状态机（pending/in_progress/blocked/verified/failed）；
- 子目标只是提示词里的一段文字，模型可以跳过、重复或自认为完成；
- `repeat_guard` 只检测“同一动作 + 同一位置/内容”，检测不到“换了三个坐标点同一个按钮”这种语义循环。

**影响**：长任务中模型会“看起来在干活”，实际上在漂移；预算烧完才发现方向错了。

**优先级：P0/P1**。这是从“能演示”到“能交付”的分水岭。

---

#### N4. 缺协议层：21 个工具，但没有一条“应用协议”

当前工具全部是项目自己封装的：文件、进程、命令、桌面控制。没有 MCP 客户端、没有 CLI 适配器、没有浏览器 DOM、没有 Excel/COM 适配器。结果是：

- 对第三方应用，默认路径是 GUI（UIA/OCR/坐标）；
- 每个应用都要靠模型“看屏幕”去理解；
- 应用升级、窗口改版、DPI 变化都会让流程失效；
- 无法复用生态里现成的 MCP Server。

外部资料显示，MCP 在 2026 年已经成为 Agent 工具集成的事实标准，甚至出现了 OSWorld-MCP 这类基准；手机端厂商也在走“Harness + 原子能力”的路线，而不是让模型点一切。**项目目前正好站在“纯 GUI”这一端，离“协议优先、模拟兜底”还有一整层。**

**影响**：成功率天花板低、token 成本高、应用漂移脆弱。

**优先级：P1（高）**。这是提升成功率最大的单一杠杆。

---

#### N5. 缺“代码即动作”：批量文件任务只能靠工具一个个做

`run_command` 是 R2 + PIN + 29 条黑名单，`write_text_file` 只能写文本，`copy_path`/`move_path` 一次一个。对于小企业最常见的任务——批量改名、按规则归档、CSV 清洗、Excel 汇总——当前只能：

- 让模型循环调用很多次文件工具（慢、贵、容易错）；
- 或者 `run_command` 写脚本（R2 + PIN，黑名单还会误伤）；
- 或者 GUI 操作 Excel（最脆弱）。

`疑问与回答.md` 提到的 CoAct-1/StateAct 路线，核心就是“能写代码就不要点屏幕”。当前项目没有“沙箱内代码执行”这一等公民。

**影响**：最匹配小企业的文件/表格任务，反而没有高效率路径。

**优先级：P1（高）**。

---

#### N6. 验证只到“文件层”，没有到“业务层”

`verification.py` 能证明：

- 文件存在、大小、哈希；
- 复制后内容一致；
- 删除后路径消失；
- 命令退出码为 0。

但不能证明：

- 金额算对了、行数对了、字段没串；
- 邮件/消息真的发出去了；
- 网页表单真的提交成功；
- Excel 里的公式/透视表结果正确；
- GUI 操作后界面真的变成了预期状态。

任务卡的机器判据支持 7 种检查（exists/absent/file_count/file_size/sha256/text_contains/text_not_contains），但没有 JSON/CSV 查询、没有合计/行数/字段匹配、没有“命令输出包含”、没有 GUI 控件值检查。**UIA 已经接入了，但 GUI 后置校验还没接**（TD-30 自己承认）。

**影响**：假成功仍然可能；模型说“已完成”，用户只能自己看。

**优先级：P0/P1**。先补 GUI 后置校验，再补业务级判据。

---

#### N7. 成本与上下文治理不足

- 历史截图只保留最近 1 张发给模型，这是对的；但截图 base64 仍然写进 checkpoint；
- `FileCheckpointSaver` 每次 `put`/`put_writes` 都把整个 `storage/writes/blobs` 序列化成一个 JSON 文件，长任务会越来越慢、越来越大；
- 没有历史摘要/截断；没有按 thread 分文件；没有清理策略；
- 没有模型路由（简单任务用 flash、难任务用 27b）；没有前缀缓存（qwen3.5-27b 官方页面甚至标注“上下文缓存不支持”）；
- 费用上限依赖 `usage_metadata`，供应商不返回时只记调用次数，不估算费用；
- 没有月度/时间窗口限流。

**影响**：长任务成本不可控；真实案例 18 步 5.87 元，单次成功成本可能超过小企业愿意支付的价格。

**优先级：P1**。先做成本仪表盘和模型路由，再谈优化。

### 3.2 产品与业务

#### N8. “小企业版”的业务内核还是演示数据

`agent/tools/agent_tools.py` 里：

- `get_weather` 返回固定天气；
- `get_user_location` 随机返回深圳/合肥/杭州；
- `get_user_id` 随机返回 1001–1010；
- `get_current_month` 随机返回月份；
- `fetch_external_data` 读 `data/external/records.csv`，但该文件是 0 字节；注解是 `str`，实际返回 `dict`；
- `app_file_uploader.py` 是空壳。

这意味着：**“小企业版”的安全壳已经建好，但业务价值层还没有接上。** 如果目标客户是真实小企业，这些工具必须换成真实数据源，或者从产品里删掉，避免误导。

**优先级：P0（如果要做产品）**。

---

#### N9. 没有交付形态：小企业装不上

当前运行方式：

- 需要 Python 3.13+/uv；
- 需要 `uv sync`；
- 需要 `uv run python scripts/apply_env_patch.py`（`uv sync` 重建后会丢失）；
- 需要 `.env` 配模型 Key；
- 需要 `scripts/setup_approval_pin.py` 设置 PIN；
- 需要命令行启动 Streamlit。

对开发者没问题，对没有 IT 的小企业用户是灾难。没有安装包、没有托盘/快捷键、没有开机自启、没有自动更新、没有日志查看器、没有备份/恢复向导。

**优先级：P1（产品化必做）**。

---

#### N10. 审批与术语不适合非技术用户

- 一次 2.5 分钟任务 20 次审批；
- 每次审批要输入 PIN（R2 动作）；
- 界面出现 R2/R3、批次号、机器判据、任务卡、回滚边界等术语；
- 没有“计划预览”（先看要做什么，再批准）；
- 没有“本次任务内允许对该窗口操作”的范围授权；
- 没有进度时间线，用户不知道现在做到哪一步。

**影响**：用户要么被吓退，要么机械点“允许”——两种结果都让安全机制失效。

**优先级：P0/P1**。这是“可用性”问题，也是“安全性”问题。

---

#### N11. 没有鉴权/多用户/租户隔离

- Streamlit 没有登录；
- `thread_id` 可由用户填写，不是身份凭证；
- 单任务锁是单机文件锁；
- 如果按文档用 `--server.address 0.0.0.0` 暴露到局域网，任何能访问端口的人都能使用当前用户的工具权限。

**影响**：只能单机单用户；不能做团队版/SaaS；局域网暴露风险高。

**优先级：P1（如果要团队部署）**。

---

#### N12. 技能库不是工作流，价值有限

- 技能只保存“步骤 + 截图 + 匹配词 + 建议动作 + 核对项”，不自动执行；
- 匹配是字符 2-gram + 包含关系，可能推荐不相关技能；
- 没有“这条技能上次成功是什么时候/成功率多少/是否过期”；
- 没有版本、没有签名、没有导入导出、没有团队共享；
- 截图和步骤是明文，可能含业务隐私；
- 长任务按子目标拆分是启发式，归属可能错。

**影响**：技能库更像“任务笔记”，不是“可复用工作流”；对成功率的提升有限。

**优先级：P2**。先把评测和协议层做好，再升级技能库。

#### N14. 文档漂移（已在 1.4 展开）

文档密度是优势，但 9,700 行文档 + 13,500 行代码，已经出现模型名、动作数、用例数、项目名四类漂移。建议：

- 数字由代码生成，不手写；

- 关键决策用 ADR（Architecture Decision Record），不要都堆在 `ARCHITECTURE.md`；
- 加“文档一致性测试”。

#### N15. 没有 CI / 类型检查 / 覆盖率门禁

- `.github/workflows` 不存在；
- 没有 `pytest.ini`/`ruff.toml`/`mypy.ini`；
- `.ruff_cache` 说明本地跑过 ruff，但没有门禁；
- 没有覆盖率统计；
- 没有依赖审计（`pip-audit`/`uv lock --check`）；
- 没有端到端冒烟测试。

**影响**：193 条用例是“手动跑的”，不是“每次提交都跑的”；回归靠自觉。

**优先级：P0（低成本、高收益）**。

#### N16. 全局状态 + Streamlit 热重载 = 真实事故源

项目已经遇到过：

- 模块热重载后旧 Agent 持有旧 `agent.guard.state`，界面写新模块、执行端读旧模块，导致“PIN 正确却一直被拒”；
- 用 `isinstance` 判断跨模块 `TaskCard` 失败，`dict(card)` 报 `'TaskCard' object is not iterable`；
- 审批上下文改成内存 + `.agent_state/approval_context.json` 双写才修好。

这些不是偶然 bug，而是“进程内全局状态 + 文件快照 + 热重载”这套架构的固有复杂度。当前用“按模块身份重建 Agent”兜住了，但每加一个全局状态，就多一个热重载陷阱。

**建议**：

- 把运行态收敛到一个 `TaskRuntime` 对象，通过依赖注入传递，减少模块级全局；
- 审批/预算/停止状态用一个明确的存储接口（内存/文件），不要散落在多个模块；
- 加一个“热重载回归用例”，模拟模块重导入。

---

#### N17. 审计与任务状态的细节问题

这是本次代码审阅新发现的几个具体问题：

1. **异常被记成 `finished`**：`execute_stream`/`resume_stream` 的 `finally` 无条件 `end_task("finished")`；如果模型调用抛异常，任务仍可能被记成 finished，而不是 failed。审计统计会失真。
2. **`step_no` 慢一拍**：`monitor_tool` 在 `guard_execute` 扣步之前取 `task.steps`，审计里的 `step_no` 是“上一步”的编号。
3. **一次任务被拆成 21 条 `task_end`**：每次 HITL interrupt 都结束一次 run，resume 再开一次；真实案例一个任务 21 条 `task_end`、20 条 `approval`。按 `batch_id` 能还原，但按 `task_end` 统计会误判。
4. **UI 操作记录可能只保留最后一段**：`app._render_events` 每次只返回当前 stream 段的 operations；`_render_hitl_block` 在 resume 后调用 `_remember_last_task`，只保存最后一段。前面 17 步可能不会出现在最终聊天记录/技能保存里（批次日志仍有）。
5. **审批上下文不是一次性凭证**：`guard_execute` 校验的是审批上下文里的 `approved_actions`，不是当前这次调用的精确 hash；同一批次的 R2 动作在恢复窗口内可复用同一授权上下文，直到 `finally` 清空/过期。

**影响**：事后取证、技能保存、成本归因都会受影响。  
**优先级**：P1（审计/状态正确性）。

#### N18. 依赖与配置卫生

`pyproject.toml` 里有几个可疑依赖：

- `callable`、`command`、`datetime`、`logger`：代码里没有直接使用；
- `datetime` 还是与标准库同名的第三方包，容易混淆/供应链风险；
- `langgraph` 没有直接声明（靠 LangChain 传递依赖）；
- `yaml.FullLoader` 仍在 `utils/config_handler.py` 使用；
- `pyproject` 要求 `>=3.13`，文档写 3.14；
- 没有依赖哈希/签名校验。

**建议**：删除未使用依赖；直接依赖显式声明；`yaml.safe_load`；`uv lock --check` + `pip-audit` 进 CI；给 `omnipilot-agent` 做供应链评估。

## 4. 结构性限制

“不足”是能补的，“限制”是当前架构/环境决定的边界。把两者分开，避免制定不切实际的路线图。

| ID | 限制 | 说明 | 影响 | 何时能改变 |
| --- | --- | --- | --- | --- |
| L1 | **L2 应用层安全** | 所有工具以当前 Windows 用户权限运行；没有 AppContainer/Job Object/VM | 黑名单/GUI 绕过最终等于当前用户权限 | 引入专用低权限用户 + 沙箱后到 L3 |
| L2 | **Windows-only** | UIA/OCR 依赖 Windows；非 Windows 不生效 | 不能跨平台；客户锁定 Windows | 短期不做，明确标注 |
| L3 | **GUI 是有损状态** | 截图/OCR 无法区分相同像素的不同程序状态 | 长任务状态漂移；误点/误输入 | 引入状态快照 + 协议层后可缓解 |
| L4 | **云端模型依赖** | 主/备模型都走 DashScope 兼容端点；无本地模型 | 数据出境/隐私；断网不可用；成本不可控 | 接入本地/私有模型 |
| L5 | **单进程 + 文件状态** | Streamlit 单 worker；任务锁是文件锁；checkpoint 是 JSON | 多标签/多实例冲突；长任务文件膨胀 | 引入 DB/队列/多 worker |
| L6 | **PIN 是同机第二主体** | 同一 Windows 用户下的恶意程序可读进程/键盘 | 挡不住蓄意攻击，只防误触/自点 | 带外审批/独立主机/硬件密钥 |
| L7 | **预算依赖 usage** | 供应商不返回 `usage_metadata` 时只记调用次数 | 费用上限可能不触发 | 换供应商或加保守估算 |
| L8 | **长任务基准现实** | OSWorld 2.0 长流程二元完成率仍显著低于短任务，且对 harness 极敏感 | 不能指望“换个模型就解决” | 靠状态 grounding + 验证 + 协议 |
| L9 | **小企业采用门槛** | 安全功能多、术语多、需要配置 | 用户可能不用/用错 | 产品化/模板化/默认安全 |

## 5. 关键取舍

这一节回答“为什么现在是这个样子，以及什么时候该改”。

| 取舍 | 当前选择 | 得到什么 | 付出什么 | 建议何时改 |
| --- | --- | --- | --- | --- |
| **安全 vs 可用** | 每个桌面输入都 HITL + PIN；观察动作也大多要确认 | 防误操作强 | 20 次审批/18 次调用；用户机械批准 | 现在就改：范围授权 + 观察免确认 |
| **通用 vs 可靠** | 21 个通用工具，GUI 操作任意应用 | 覆盖面广、演示效果好 | 成功率低、成本高、应用漂移脆弱 | 现在就改：协议优先，GUI 兜底 |
| **成本 vs 精度** | 只保留最近 1 张截图；主模型 27b；无多 rollout | 成本可控 | 旧现场丢失、模型可能重复截图；单次方差大 | 先做状态摘要/区域截图/模型路由 |
| **本地 vs 云** | 全部走云端模型 | 能力强、接入快 | 隐私/合规/断网/成本 | 有敏感客户时接本地模型 |
| **简单 vs 稳健** | 单进程 + 文件状态 + JSON checkpoint | 易部署、易调试 | 多实例/长任务/热重载问题 | 团队版/长任务前改 DB/队列 |
| **自主 vs 控制** | 逐步审批，没有计划审批 | 控制强 | 用户成为瓶颈；模型没有全局计划 | 现在加“计划预览 + 范围执行” |
| **广度 vs 深度** | 26 个桌面动作、21 个工具 | 能力看起来全 | 没有一个流程做到高成功率 | 现在砍到 3 个核心工作流 |
| **快速卡 vs 合同** | 快速卡默认允许全部动作，只禁止“提权” | 上手快 | “合同”名不副实；安全承诺弱 | 改成模板化默认范围，或改名“任务说明” |

### 5.1 最尖锐的一组取舍：安全 vs 审批疲劳

当前设计的隐含假设是：**确认次数越多，系统越安全。** 真实数据不支持这个假设：

- 18 次工具调用 → 20 次审批；
- 用户最后两次直接拒绝；
- 外部研究（NIST 相关讨论、2026 年多篇 HITL 研究）把这种现象叫 **approval fatigue / consent fatigue**：审批密度超过阈值后，安全性随审批次数呈倒 U 型下降；
- 更有效的做法不是“增加确认”，而是“减少确认次数、提高每次确认的信息量和约束力”：范围授权、一次性凭证、精确绑定、只拦不可逆/对外副作用。

**建议**：把“每步确认”改成“任务级/窗口级范围授权”。例如：

> “允许本任务在「微信」窗口内点击/输入，最多 10 步，有效期 10 分钟；发送消息前仍需人工确认。”

这比 20 张“输入文字/点击坐标”的卡片更安全，也更可用。

### 5.2 第二尖锐的取舍：通用 vs 可靠

“能操作所有软件”是卖点，也是可靠性陷阱。当前没有协议层，所有第三方应用都走 GUI；GUI 的成功率取决于：

- 应用是否暴露 UIA 控件；
- OCR 是否识别得准；
- 窗口是否在前台；
- DPI/多显示器是否一致；
- 应用版本是否变化。

**建议**：明确“协议优先、模拟兜底”的路线。对 Top 3 应用做适配器（Excel/浏览器/文件管理器），把 GUI 留给没有接口的应用（如微信）。这不是放弃通用性，而是把通用性放在正确的层级。

### 5.3 第三尖锐的取舍：快速卡 vs 合同

快速卡默认 `allowed_actions = ALL_ACTIONS`、`forbidden_actions = ["提权"]`、没有输入/输出范围、没有机器判据。它实际上是一张“任务说明”，不是“范围合同”。文档却把它叫“合同”，容易让用户以为“系统已经限制了范围”。

**建议**：

- 要么给快速卡加“按任务类型的默认范围”（文件任务：输入目录/输出目录；桌面任务：应用白名单）；
- 要么在 UI 上明确写“快速卡只记录目标，不限制范围；需要强约束请用自定义卡”；
- 不要用“合同”这个词去描述一张没有范围的卡。

## 6. 与《疑问与回答》的三层框架对照

你提供的《疑问与回答》把 Computer-Use Agent 的失败分成三层：**看错（Grounding）/ 想错（State）/ 错上加错（Recovery）**。用这个框架看当前项目，结论很清楚：

| 层 | 文档建议 | 项目现状 | 差距 |
| --- | --- | --- | --- |
| **Grounding** | UIA/DOM 优先，SoM/混合定位，坐标最后 | UIA/OCR 已接入，坐标兜底；无 DOM/SoM；OCR 在真实任务中两次找不到“搜索” | **部分落地** |
| **State** | 状态优先，能读程序状态就不要猜截图；FSM/状态校验 | 任务卡 + 子目标提示；没有状态快照、没有 FSM、没有“无进展”检测；截图仍是主证据 | **基本缺失** |
| **Recovery** | Loop Breaker + 独立验证器；失败后换策略 | 重试/重复拦截/会话自愈都有；但重复拦截只提醒，没有强制换策略；没有独立验证器 | **部分落地** |
| **Test-time** | 多 rollout/MCTS | 没有；预算也不支持 | **不做（合理）** |
| **Protocol** | 协议优先、模拟兜底 | 无 MCP/CLI/DOM；GUI 是主路径 | **缺失** |
| **Permission** | 权限分层、应用声明、人工确认 | R0–R3 + 任务卡 + PIN；没有应用级声明/OS 隔离 | **部分落地** |

**一句话总结**：**项目采用了三层框架的词汇，但只落地了第一层和第三层的一半；第二层（状态 grounding）基本缺失，所以长任务仍然靠运气。**

## 7. 外部参照（2026 年）

外部资料不是用来“抄答案”的，而是用来校准方向。以下几条与项目最相关。

### 7.1 OSWorld / OSWorld 2.0：长任务仍然是行业难题

- OSWorld-Verified（短任务）头部 Agent 已经能到 90% 左右；
- OSWorld 2.0（长流程、多应用、几百次工具调用）的二元完成率明显低得多；不同来源对前沿系统的数字差异很大（约 20%–70%），取决于模型版本、harness、离线子集和步数预算；
- 部分分（partial score）通常高得多，说明“做了很多，但没全对”是常态。

**对项目的含义**：不要拿“某个 benchmark 分数”做产品承诺；先在自己的 20 个任务上测出 baseline。长任务失败不是“模型不够聪明”这么简单，而是状态/验证/协议的系统问题。

### 7.2 MCP：协议层已经是事实标准

- MCP 在 2026 年已经被主流平台广泛支持，工具/资源/提示词有统一协议；
- 甚至出现了 OSWorld-MCP 这类“用 MCP 工具做电脑操作”的基准；
- 手机端厂商的 Harness 路线也是“把系统能力封装成工具”，而不是让模型点一切。

**对项目的含义**：先接 2–3 个高价值 MCP Server/适配器（文件系统、浏览器、Excel/数据库），把 GUI 留给没有接口的应用。MCP 不是免费的安全：需要 server allowlist、tool annotation、权限映射（只读/写/破坏性）和审计。

### 7.3 OS 级沙箱：从 L2 到 L3 是行业方向

- 微软在 2026 年推出 Microsoft Execution Containers（MXC）/Agent 365，强调“系统执行策略，不依赖模型自觉”；
- OpenAI Codex 的 Windows 沙箱使用专用低权限账户 + 受限令牌 + 防火墙规则；
- 这些方案的共同点是：**不再把“确认卡片”当安全边界，而是把权限收在 OS 层。**

**对项目的含义**：最低成本可以先做“专用非管理员用户 + Job Object + 受限令牌 + 防火墙”；不要继续用“再加 20 条正则”替代沙箱。

### 7.4 审批疲劳：确认越多，不一定越安全

- 2026 年多篇 HITL 研究/业界综述指出：审批密度过高会导致机械批准，安全性呈倒 U 型；
- 推荐做法：只拦不可逆/对外副作用；对重复动作给“审批范围”；把决策上下文放进请求，而不是让审批人自己找；
- NIST 在讨论 Agentic AI 身份与授权时也提到 consent fatigue，并讨论“预批准 flight plan”的方向。

**对项目的含义**：当前 20 次审批/18 次调用是典型反例。应改为“范围授权 + 一次性凭证 + 精确绑定”，而不是继续增加确认。

### 7.5 Agent 评测：结果、过程、风险、成本四层

外部评测方法普遍强调：

- 任务成功率（TSR）只是第一层；
- 还要看步骤完成率、工具调用准确率、首次成功率、稳定性（重复运行）；
- 要看风险行为（越权、泄露、不可逆操作）；
- 要看单次成功成本、P50/P95 时延、人工介入次数；
- 优先用“环境状态验证”，不要用模型自评。

**对项目的含义**：当前的 193 条用例是“单元测试”，不是“Agent 评测”。需要补一层真实任务评测。

## 8. 建议路线图

### 8.1 先选路线：产品还是参考架构？

| 路线 | 适合目标 | 应该做什么 | 不应该做什么 |
| --- | --- | --- | --- |
| **A. 小企业产品** | 卖给 3–10 人小团队 | 砍到 3 个核心工作流；协议优先；代码即动作；安装包；范围授权；OS 沙箱 | 不要追求“操作所有软件”；不要做发消息/付款全自动 |
| **B. 个人效率工具** | 自己/极客用户 | 保留广度；补评测；补观察免确认；补 GUI 后置校验 | 不要做多用户/鉴权/复杂部署 |
| **C. 参考架构/学习项目** | 教学、面试、技术影响力 | 保留文档和守卫层；补 ADR；补评测；不要产品化 | 不要用“生产级安全”宣传 |

**我的建议**：如果目标是“小企业版”，选 A；如果目标是“把项目作为能力样板”，选 C。当前最危险的是“用 A 的叙事，做 C 的深度，却没有 A 的验证”。

### 8.2 P0：0–2 周，先“可测量 + 止血”

| # | 动作 | 具体做法 | 验收标准 |
| --- | --- | --- | --- |
| 1 | **建真实评测尺** | 20–30 个任务（文件整理/CSV 报表/固定桌面流程），每个 3 次；用临时工作区、真实模型、环境状态验证；记录 success/partial/steps/cost/latency/interventions/unsafe | 产出 baseline JSON；能回答“当前成功率是多少” |
| 2 | **堵秘密读取** | `guard_path` 增加读侧秘密文件拒绝（`.env`、`*.key`、`*.pem`、`credentials*`、`id_rsa*`）；`read_text_file`/`search_text` 同步；默认工作区改成“一个输入目录 + 一个输出目录” | 探针读 `.env` 被拒；审计/日志 grep 不到密钥 |
| 3 | **审计脱敏与状态修正** | `sanitize_tool_args` 覆盖所有工具（写文件内容哈希/长度、命令脱敏、URL 域名）；`log_approval` 只记动作名+参数哈希；异常时 `end_task("failed")`；修正 `step_no` | 审计无原文；强制异常显示 failed；回放 step 对齐 |
| 4 | **审批范围授权 v1** | 新增 `ApprovalGrant`：应用/窗口 + 动作类别 + 路径范围 + 最大步数 + 有效期 + 次数；`guard_execute` 绑定当前调用 hash 并扣减次数；观察动作（`screenshot`/`ui_tree`/`ui_windows`/`ocr_text`）在任务卡允许“桌面观察”时免逐次确认，`clipboard_get` 仍确认 | 10 步 GUI 任务 ≤2 张审批卡；R2 无 grant 必拒；token 重放必拒 |
| 5 | **原始输入绑定窗口** | `type_text`/`press_key`/`hotkey`/raw `click` 执行前解析前台窗口并过 `_guard_ui_target`；确认卡片显示目标窗口标题/pid；不允许“当前焦点未知”时输入 | 终端前台 + `type_text` 被拒；确认卡片能看出目标窗口 |
| 6 | **GUI 后置校验** | `ui_click`/`ui_set_text` 后检查目标控件存在/值变化/窗口标题变化；无法确认时标 `unconfirmed`，不得说“完成” | 常见控件操作有 pass/fail/unconfirmed 三态 |
| 7 | **CI 与依赖卫生** | GitHub Actions：unittest + ruff + pyright + `uv lock --check` + `pip-audit`；删除 `callable`/`command`/`datetime`/`logger`；`yaml.safe_load` | PR 红灯；`uv tree` 干净 |

### 8.3 P1：1–3 个月，补“能力内核”

| # | 动作 | 具体做法 | 验收标准 |
| --- | --- | --- | --- |
| 8 | **协议层** | MCP client + 2–3 个 server（文件系统、浏览器 DOM、Excel/数据库）；CLI 适配器（ffmpeg/7z/git 等）；工具路由器：协议 > CLI > UIA > OCR > 坐标 | 3 个核心工作流走协议路径；成功率提升、成本下降 |
| 9 | **代码即动作** | 新增 `run_script`：脚本写入专用目录、内容展示+哈希+审批、Job Object 限资源、禁网、输出上限、diff/回滚；同一 hash 在任务内可复用授权 | 1,000 文件批量任务 <1 分钟；可回滚；无法越界 |
| 10 | **状态 grounding** | 每步记录前台窗口/pid/焦点控件/UIA 树哈希/截图哈希/文件统计；连续 N 步无变化 → 触发换策略/停下问人；子目标状态机 pending/in_progress/blocked/verified/failed | 真实任务“无进展”能被检测；子目标状态可见 |
| 11 | **独立验证器** | 规则优先；必要时用不同模型/不同提示词做第二验证；输出 `passed/failed/unconfirmed`；`unconfirmed` 不得当完成 | GUI 任务验证覆盖率 >70%；假成功 <5% |
| 12 | **OS 级隔离** | 专用非管理员 Windows 用户 + Job Object + 受限令牌 + 防火墙；Win11 可评估 MXC/AppContainer | 命令无法写出工作区/联网；资源限制生效；逃逸测试失败 |
| 13 | **上下文/成本治理** | 历史摘要；截图移出 checkpoint 或定期清理；SQLite/Postgres；成本仪表盘；模型路由（简单 flash/难 27b） | 60 步任务内存/文件可控；单次成功成本 <¥1 |
| 14 | **产品化收口** | 安装包/托盘/快捷键/自启；3 个模板；去掉 R2/R3 术语；日志查看器；备份/恢复 | 非技术用户 30 分钟内完成 3 个任务 |

### 8.4 P2：3–6 个月，做“可运营”

- 技能库 v3：带成功率/最后验证时间/版本/签名/导入导出/团队共享；
- 多用户/鉴权/租户隔离（如果做团队版）；
- OpenTelemetry 指标/追踪；WORM/SIEM；DLP；数据保留期；
- 本地模型/私有部署选项；
- 跨平台或明确 Windows-only。

### 8.5 阶段门（不要跳过）

| 门 | 条件 | 不满足时 |
| --- | --- | --- |
| G1 基线 | 20 个任务 × 3 次，有 success/cost/interventions | 不允许加新工具 |
| G2 核心流程 | 3 个流程 ≥80% success；假成功 <5%；≤2 次介入/任务 | 缩窄范围或换协议路径 |
| G3 安全 | `.env` 读拒绝；审计无原文；R2 全部有 grant；沙箱逃逸测试通过 | 不允许对外演示 |

## 9. 不建议做的事

1. **不要再用“加正则/黑名单”当安全边界。** 命令黑名单是启发式，`python -c`、`powershell -Command`、GUI 输入都能绕过；真正的边界是沙箱 + 权限 + 审批。
2. **不要在没测 baseline 之前继续加工具/动作。** 26 个动作已经很多，缺的不是数量，是可靠性。
3. **不要追求 OSWorld 榜单分数。** 你的客户不关心 benchmark；他们关心“这 3 个任务能不能稳定完成”。
4. **不要把“每步确认”当成安全。** 20 次审批会让用户机械批准；范围授权 + 精确绑定才是正解。
5. **不要把技能库做成自动执行器。** 没有验证的旧经验会自动把错误放大；技能只能是提示，必须经过当前任务卡/确认/验证。
6. **不要把 PIN 当成恶意软件边界。** 同一 Windows 用户下的程序可以读进程/键盘；PIN 只防误触和“模型自己点确认”。
7. **不要把 Streamlit 暴露到局域网/公网而不加鉴权。** 任何能访问端口的人都能用当前用户的工具权限。
8. **不要在不可信电脑上处理客户隐私/付款/凭据。** 当前是 L2，不是沙箱；这是安全报告自己的结论。
9. **不要用“任务卡”这个词去描述一张没有范围的快速卡。** 要么加范围，要么改名，避免虚假安全感。
10. **不要把所有东西都塞进 `ARCHITECTURE.md`。** 历史叙事进 CHANGELOG，关键决策进 ADR，数字由代码生成。

## 10. 结论

### 10.1 三句话

1. **这个项目最值钱的不是 21 个工具，而是“确定性守卫 + 失败韧性 + 审计”的工程纪律。** 这套纪律应该保留，不要因为追求能力而拆掉。
2. **它现在最大的问题不是“不够安全”，而是“安全壳跑在能力内核前面”。** 没有真实评测、没有状态 grounding、没有协议层、没有独立验证器，所以长任务仍然靠运气。
3. **下一步不是加更多功能，而是把“可测量、可授权、可协议化”这三件事做成。** 先测，再改；先缩范围，再谈通用。

### 10.2 一句话定位

> **把它当成“一个需要人看着的本地文件/桌面助手”，而不是“能替你处理秘密和付款的安全代理”。**  
> 在可信电脑、可信用户、可撤销文件任务里，它已经能省时间；在客户数据、财务、凭据、无人值守任务之前，先完成 P0 加固和真实评测。

### 10.3 下一步建议

如果只做一件事：**先建 20 个真实任务的评测尺，跑 3 次，拿到 baseline。**  
如果做两件事：**评测尺 + 范围授权。**  
如果做三件事：**评测尺 + 范围授权 + 一个协议适配器（浏览器或 Excel）。**

这三件事做完，你才有资格回答“这个项目到底能不能成为产品”；在此之前，所有“成功率提升”的说法都只是故事。
