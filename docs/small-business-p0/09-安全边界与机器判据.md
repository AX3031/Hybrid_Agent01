# 09 安全边界、审批验签与机器判据（2026-10-27 补强）

> 这篇讲清楚这一轮补了什么、为什么补、怎么验证、还差什么。
> 面向入门读者：先看“一句话”，再看场景和例子；开发者可以直接看第 8 节代码地图。

## 1. 一句话

这一轮把五个“看起来有、其实不够硬”的地方补成了代码级检查：

1. Agent 不能再写项目源码、配置、提示词、脚本、`.venv`、`.git`、`logs/`、`memorys/` 等；
2. R2/R3 的审批凭证不再“有个 token 就放行”，而是验 HMAC、有效期、任务、批次、动作；
3. 复制/移动文件或目录时，目标或源目录树里有可执行后缀就拒绝；
4. 任务卡禁止“发送/提交/付款”时，所有 GUI 输入类动作保守拒绝；
5. 每个新任务都必须有任务卡；写入/命令/打开类必须有机器判据，任务结束由代码核对，工具失败/未确认不能算完成。

同时把“回滚边界”写清楚：文件类可回滚，命令/GUI/永久删除/大文件覆盖不可回滚。

---

## 2. 为什么这五件事要补

上一版已经有任务卡、PIN、批次回滚、预算、审计，但有几个真实的“缺口”：

| 缺口 | 现实后果 |
| --- | --- |
| Agent 能写项目源码/配置/日志 | 被诱导后可以改守卫代码、改 `read_only`、改提示词，甚至写 `.venv` 的 `.py`/`.pth`，下次启动生效 |
| 审批只检查 token 非空 | 同进程任何代码塞一个假 token 就能过；HMAC 只是“写了但没验” |
| 复制/移动不查后缀 | `note.txt` 复制/改名成 `note.bat`，再执行，绕过“写脚本”拦截 |
| 任务卡写“禁止发送/付款”但 GUI 不认 | 用户以为已经禁止，实际点击/输入仍能发送或付款 |
| 任务卡成功判据只是提示词 | 模型说“完成”就交付，文件没对上/少一行/金额错了也发现不了 |

这一轮的目标不是“再加功能”，而是把这几条从“提示词/约定”降到“确定性检查”。

## 3. 项目自身写保护

### 3.1 保护哪些位置

`agent/tools/safety.py` 新增 `is_project_protected(path)`，写操作经过 `guard_path(..., for_write=True)` 时检查：

```text
agent/ config/ prompts/ scripts/ utils/ model/ memorys/ env_patch/ tests/
.venv/ .git/ .github/ logs/ .idea/ .vscode/
app.py main.py test1.py app_file_uploader.py pyproject.toml uv.lock
.env .gitignore AGENTS.md README.md CHANGELOG.md 等根目录源码/配置
```

判断依据是“相对项目根的路径”，不是简单匹配目录名；所以工作区里另一个同名 `logs/` 不会被误伤。

### 3.2 两条防线

1. **路径工具**：`write_text_file`、`create_directory`、`move_path`、`copy_path`、`delete_path` 的目标经过 `guard_path(..., for_write=True)`，命中项目保护路径直接拒绝。
2. **命令工具**：`run_command` 的 `check_command()` 会识别命令文本里的项目受保护路径/根文件，拒绝 `Set-Content config/agent.yml ...`、`copy a.txt logs/x.txt` 等写法。

### 3.3 例子

```text
write_text_file("config/agent.yml", ...)
→ 该路径属于项目源码/配置/提示词/脚本/日志/虚拟环境/Git 元数据，Agent 不得写入

run_command("Set-Content config/agent.yml ...")
→ 该命令引用了项目源码/配置/...，已拒绝
```

### 3.4 还没覆盖的

- **读**：`.env` 仍可能被 `read_text_file`/`search_text` 读取；这一轮只禁止写。
- **`data/` 输出目录**：允许写；如果任务允许写 `.py` 到 `data/`，仍可能被后续命令执行（需要命令白名单/输出目录约束）。
- **同用户外部程序**：项目保护只约束 Agent 工具，不约束同一 Windows 用户下的其他程序。

## 4. 审批凭证真正验签

### 4.1 以前的漏洞

`guard_execute` 原来只做：

```text
context = approval_context(tool_name)
if not context.get("token"): 拒绝
```

也就是说：只要内存里有个非空字符串，R2/R3 就能执行。HMAC 凭证虽然生成了，但执行侧没有验。

### 4.2 现在怎么验

- `approval.verify_approval_token()` 支持 `thread_id / batch_id / actions` 绑定；
- `guard_execute` 执行 R2/R3 前校验：
  - 签名是否由本机密钥生成；
  - 是否在 10 分钟有效期内；
  - `thread_id` 是否等于当前任务；
  - `batch_id` 是否等于当前批次；
  - `actions` 的参数摘要是否与当前批准的动作一致。

### 4.3 例子

```text
用户批准 run_command：批准凭证绑定 thread=g6、batch=BGUARD-6、command=echo hi
执行时：
  - 假 token → 拒绝
  - 换了命令 → 参数摘要不一致 → 拒绝
  - 换了任务/批次 → 拒绝
  - 超过 10 分钟 → 拒绝
```

### 4.4 仍然存在的边界

- PIN 仍是同机、同浏览器；挡不住同一 Windows 用户下的恶意程序；
- `approval_token` 仍可能写进审计日志（HMAC，不是 PIN），日志读取面仍在；
- 同进程恶意代码理论上仍可调用 `sign_approval`；这不是独立主机隔离。

## 5. 复制/移动的可执行后缀拦截

### 5.1 文件级

`copy_path` / `move_path` 在解析最终目标后调用 `check_write_suffix(dst)`：

```text
copy_path("note.txt", "note.bat") → 拒绝
move_path("note.txt", "note.ps1") → 拒绝
```

### 5.2 目录级

如果复制/移动的是目录，`check_tree_write_suffix(src)` 会遍历源目录树；只要里面有一个 `.bat`/`.ps1`/`.exe` 等，就拒绝整个复制/移动。

### 5.3 命令级

`check_command` 新增规则：`copy` / `move` / `xcopy` / `robocopy` 到可执行后缀直接拒绝，避免绕过工具层。

### 5.4 仍然存在的边界

- 17 种可执行后缀是黑名单；未列出的解释器/脚本类型仍需命令白名单/内容检测；
- 复制一个已有 `.bat` 到输出会被拒绝；如果业务确实需要，必须显式改策略，而不是静默放行。

## 6. GUI 的“禁止发送/付款”怎么落地

### 6.1 为什么不能做“语义识别”

`computer_use` 只知道“在坐标 (x,y) 点击”或“向当前焦点窗口输入文字”，它不知道这个按钮是“发送”还是“保存”。所以不能假装任务卡写了“禁止发送”就真的能识别发送。

### 6.2 现在的保守策略

如果任务卡的禁止动作里包含 `发送`、`提交`、`付款` 中任意一个，`policy.check_task_card()` 会拒绝所有 **GUI 输入类动作**：

- 点击、双击、右键、拖拽、滚动；
- 键盘输入、按键、组合键；
- 写剪贴板；
- 启动/关闭应用。

只读动作（截图、看分辨率、找图、等待、读剪贴板、列应用）不受这条语义禁令影响。

### 6.3 怎么允许 GUI

如果确实要做 GUI 输入，必须从任务卡的禁止动作里移除这些语义词，保留“桌面”类别，并理解最后仍由人工确认 + PIN 把关。

### 6.4 仍然存在的边界

- `run_command` / `open_path` 仍可能发送/付款；它们不在 GUI 语义拦截内，只能靠人工确认 + PIN、命令白名单/出口白名单；
- 这条策略是“保守拒绝”，不是“智能识别”；它会让默认任务卡下的 GUI 输入不可用，这是有意的安全取舍。

## 7. 任务卡全覆盖、机器判据与回滚边界

### 7.1 每个新任务都必须有任务卡

- `state.start_task()`：新任务没有 `task_card` 直接 `ValueError`；
- `app.py`：发送前检查 `TaskCard.from_dict(...)`，没有卡就 `st.stop()`；
- 只读任务也要选「读」并写成功判据；
- 写入/命令/打开类还必须有至少一条机器判据。

### 7.2 机器判据格式

一行一条，`类型|路径|期望值`：

```text
exists|D:\输出\结果.xlsx
absent|D:\输出\临时文件
file_count|D:\输出|3
file_size|D:\输出\结果.xlsx|10240
sha256|D:\输出\结果.xlsx|64位十六进制
text_contains|D:\输出\结果.txt|核对通过
text_not_contains|D:\输出\结果.txt|失败
```

- 路径必须在工作区域内；
- 解析失败、路径不在工作区、期望值格式不对，任务卡不能启用；
- 任务结束由 `agent/guard/criteria.py` 执行；
- 结果分 `passed / failed / unconfirmed / missing`；
- 有工具失败/被拒绝时，验证事件强制 `failed`，不能算完成。

### 7.3 回滚边界

`agent/guard/scope.py` 明确：

```text
可回滚：写入/覆盖/追加、建目录、移动、复制、删除到回收区
不可回滚：run_command、open_path、computer_use、永久删除、>10 MB 覆盖、应用内状态
```

任务卡提示词、确认卡片、README、OS_TOOLS 都会显示这条边界，避免用户把“整批回滚”误解成“所有操作都能撤销”。

### 7.4 仍然存在的边界

- 机器判据只能证明文件/字段对上，不能证明业务语义正确；
- GUI 任务通常没有机器判据，只能标未确认；
- 读操作没有机器判据；只读任务的“完成”仍需要人看；
- 命令退出码 0 不代表业务产物正确。

## 9. 验证与自我反思

### 9.1 本轮验证

```powershell
uv run python -m unittest discover -s tests -v
uv run python scripts/verify_small_business.py
```

当前结果：

- 全部用例 **67 条通过**；
- P0 守卫层 **47 条通过**；
- 新增覆盖：项目写保护、审批凭证绑定/假 token、复制/移动后缀/目录树、GUI 语义禁令、任务卡必填、机器判据、回滚边界。

> 具体证据文件：`docs/small-business-p0/evidence/verify-20261027-154810.json`（67/67，P0 47/47）；若数字变化，以脚本输出为准。

### 9.2 做得好

1. 每一条都落到了代码，不是只改提示词。
2. 先用失败用例复现：假 token 能过、`copy .txt→.bat` 能过、默认任务卡下 GUI 仍能输入；改完再跑全量。
3. 回滚边界写进任务卡/确认卡片/文档，避免“以为能撤”的误解。
4. 机器判据与工具失败计数结合，避免“文件存在但工具报错”被当成完成。

### 9.3 还不够

1. **`.env` 仍可读**：这是下一轮最优先的秘密文件读取拦截。
2. **日志仍记录原始参数**：`log_approval` 的 `actions`、`read_text_file` 摘要可能落盘；需要统一脱敏。
3. **命令/打开程序的“发送/付款”语义仍未拦截**：GUI 已保守拒绝，命令/URL 仍靠人工确认 + PIN。
4. **`.py`/`.pth` 仍允许写到 `data/` 等非保护目录**：需要输出目录白名单/后缀策略。
5. **同用户恶意程序仍不可防**：PIN 不是独立主机；需要带外审批/专用用户/沙箱。
6. **没有真实 30 次端到端**：67 条是离线用例，不等于真实场景成功率。

### 9.4 一句话记住

**能验签、能拦截、能对账、不能假装完成；边界写清楚，比“感觉安全”重要。**
