# 07 第二主体审批口令（P0-4）

## 1. 为什么“点确认”不够

原来的确认卡片只有一个「我确认，执行」按钮。问题是：

- 人会手滑，闭眼连点；
- 如果 Agent 能控制鼠标键盘，它理论上可以自己点掉这个按钮；
- 更隐蔽的是：Agent 可能直接改审批状态文件，把“待批”改成“已批”。

小企业版的主要风险是**误操作**，不是定向攻击。所以第二主体的目标是：**防误触 + 防自欺**。

## 2. 哪些动作需要 PIN

按可逆性分级 R0–R3：

| 级别 | 例子 | 需要 PIN？ |
| --- | --- | --- |
| R0 只读 | 读文件、截图、查系统信息 | 否 |
| R1 可撤销 | 新建文件、建目录、复制、移动、删除到回收区、覆盖（有备份） | 否（但仍需确认） |
| R2 难逆 | 执行命令、打开程序、鼠标/键盘/剪贴板写入、应用启停 | **是** |
| R3 不可逆 | 永久删除 | **是，且回滚无法恢复** |

分级代码：`agent/guard/policy.py` 的 `reversibility_of()`。

## 3. PIN 存在哪

默认目录：

```text
%PROGRAMDATA%\OSGuiAgent\approval\
  ├── pin.json        # 盐 + PBKDF2 哈希，不存明文
  ├── key.bin         # HMAC 签名密钥（32 字节随机）
  └── approvals.jsonl # 审批记录（带签名凭证，不含 PIN）
```

如果 ProgramData 不可写，退回 `%LOCALAPPDATA%\OSGuiAgent\approval`。

**Agent 工具不能读写这个目录**：

- `guard_path()` 对审批目录直接拒绝；
- `check_command()` 拒绝包含审批目录路径的命令；
- 因此 PIN 不在提示词、不在工作区、不在对话历史。

## 4. PIN 怎么存

- 6–64 位；
- 拒绝 `123456`、`password`、字符过于单一的口令；
- 使用 PBKDF2-HMAC-SHA256，随机盐，20 万次迭代；
- 只保存哈希；
- 校验用 `hmac.compare_digest`，防时序攻击。

## 5. 设置口令

```powershell
uv run python scripts/setup_approval_pin.py
```

- 输入两次，输入时不显示；
- 只保存哈希，忘记只能重设；
- 重设：加 `--force`；
- 查看状态：加 `--status`。

**不要把 PIN 写进 `.env`、README、提示词、聊天记录或 Git。** 它不是 API Key，泄露了就等于第二主体失效。

## 6. 审批流程

```text
模型请求 run_command / 永久删除 / 桌面输入
  → guard_preflight（范围/预算检查）
  → HumanInTheLoopMiddleware 挂起
  → 界面显示确认卡片 + 「审批口令」输入框
  → 用户输入 PIN
      ├─ 未设置 PIN：批准按钮禁用（fail closed）
      ├─ PIN 错误：操作不执行，可重试
      └─ PIN 正确：生成 HMAC 凭证 → 恢复执行
  → guard_execute 再检查 + 计步
  → 工具执行
```

签名凭证包含：

- 会话 ID、批次号；
- 每个动作的名称 + 参数 SHA-256；
- 时间戳、随机 nonce；
- HMAC-SHA256 签名。

审计只记录凭证，不记录 PIN。凭证有 10 分钟有效期（用于校验）。

### 6.1 凭证怎么从界面传到执行端（2026-10-28 修复）

审批通过后，`state.set_approval_context()` **同时写内存和**
`.agent_state/approval_context.json`（原子替换，15 分钟过期）；
执行侧的 `approval_context()` 内存没有就回落读这个文件。

为什么不能只放内存：Streamlit 检测到本地模块文件变化时会卸载并重新导入模块，
但 `st.session_state` 里缓存的旧 Agent 不会重建——旧中间件仍持有旧
`agent.guard.state` 模块。只放内存就会出现「PIN 正确、凭证也生成了，
执行端却说没有凭证」（真实事故：2026-10-28 打开微信连续 5 次被拒）。

安全边界：

- 文件里只有 HMAC 凭证摘要，**没有 PIN**；
- 执行端仍会验签并校验任务/批次/动作绑定，伪造文件过不了；
- 过期（15 分钟）或损坏的文件会当作没有，并尽量清理；
- 界面侧还会按 `agent.guard_state is 当前模块` 判断旧 Agent 是否已与模块
  脱节，脱节就重建 Agent 并取消上一轮未完成的确认（那种确认属于旧实例，
  checkpoint 也用不了）。


## 7. 为什么 PIN 不能防住所有事

必须诚实：

- 同一个 Windows 用户下的恶意程序可以读进程内存、记录键盘、删改文件；
- PIN 挡不住这些；
- 它挡住的是：Agent 自己点确认、Agent 改写审批状态、人闭眼连点。

要挡蓄意攻击，需要：

- 独立 Windows 用户 / 独立主机；
- 手机或 IM 带外审批；
- 硬件密钥（FIDO2）；
- 独立会话 + 签名令牌 + WORM 审计。

这些属于企业版，不在小企业版 P0。

## 8. 代码与用例

| 文件 | 作用 |

| `agent/guard/approval.py` | PIN 哈希、校验、HMAC 凭证、审批目录保护 |
| `agent/guard/state.py` | 审批上下文：内存 + 落盘副本（跨模块重载）、执行侧读取 |
| `agent/guard/policy.py` | R0–R3 分级、`requires_second_subject` |

| `scripts/setup_approval_pin.py` | 交互式设置口令 |

用例（`SecondSubjectTest`）：

- 哈希文件不包含明文；
- 错误 PIN 校验失败；
- 签名凭证可验证、伪造失败；
- Agent 读取审批目录被拒绝；
- 弱口令被拒绝。

用例（`GuardMiddlewareOrderTest`，跨模块重载回归）：

- 新模块写入的凭证，旧模块（中间件侧）也能读到；
- 工具名不匹配时不放行；
- 热重载后 R2 动作仍能通过验签并真正执行；
- 过期或已清理的落盘副本不会被误用。

## 9. 边界

1. **同机第二主体**：不是独立用户/独立主机，挡不住同用户恶意程序。
2. **忘记无法找回**：只能重设。
3. **PIN 输入在同一个浏览器会话**：如果浏览器被控制，PIN 可能被截获；需要更强隔离时走带外审批。
4. **审批一次批准一批**：同一批待确认动作共用一个 PIN；不是逐动作输入。
5. **不记录 PIN 到审计**：只记录 HMAC 凭证；但凭证本身可用于证明“这次批准发生过”。

## 10. 一句话记住

**PIN 不是密码管理器，它是让“随手点确认”变成“必须停下来输入一个只有人知道的东西”。**
